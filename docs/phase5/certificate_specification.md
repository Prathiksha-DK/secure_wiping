## Overview

A SecureWipe Sanitization Certificate is a structured, machine-readable record that documents the outcome of a storage device sanitization operation. It is generated by the **Certificate Engine** upon successful completion of a wipe-and-verify cycle and provides:

- A structured record of what was done, to what device, when, and by whom
- An assurance status indicating the outcome and its implications
- A SHA-256 integrity digest to detect post-generation tampering
- Sufficient detail to support audit, evidence, and lifecycle decision-making

**What a certificate is:**
- A structured sanitization evidence record
- An integrity-protected document (tamper-detectable)
- A point-in-time record of the operation outcome

**What a certificate is not:**
- A third-party certification or government approval
- A cryptographically signed document (digital signature infrastructure not yet deployed)
- A guarantee of physical NAND erasure for SSD/Flash/NVMe devices (see assurance status `SANITIZATION_NOT_VERIFIABLE`)
- A legally binding document without further organizational and legal context

```
Sanitization Operation Completes
             ↓
Verification Phase Runs
             ↓
CertificateEngine.generate(operation_id, operator_id, org_id)
             ↓
   ┌──────────────────────────────────┐
   │   Field Population               │
   │   - Device metadata              │
   │   - Operation details            │
   │   - Verification results         │
   │   - Recovery assessment          │
   │   - Assurance status assigned    │
   └──────────────────────────────────┘
             ↓
   SHA-256 Digest Computed
             ↓
   Certificate Stored → compliance.db
             ↓
   Audit Event Written
             ↓
   Certificate Available (API / UI / Export)
             ↓
   [Optional] Lifecycle Decision Engine consumes certificate
             ↓
   [Optional] Integration Adapter submits to external system
```

## Assurance Status Values

The `assurance_status` field carries one of four defined values. Selection is determined by the Certificate Engine based on verification results, recovery assessment, and the storage class of the device.

---

### `SANITIZED_REUSABLE`

**Meaning:** The sanitization operation completed successfully. Verification confirmed the absence of recoverable data. The recovery assessment (if performed) found no recoverable fragments. The device is assessed as suitable for reuse or resale subject to applicable policy.

**Criteria:**
- Operation completion status: `COMPLETED`
- Error count within policy-acceptable threshold
- `verification.residual_data_detected` = `false`
- `verification.verification_confidence` >= policy minimum
- Recovery score (if assessed) below policy threshold

**Implication for lifecycle:** Device may proceed to reuse, resale, or secure disposition per organizational policy.

---

### `SANITIZATION_NOT_VERIFIABLE`

**Meaning:** The sanitization method was applied, but independent verification that physical data has been erased cannot be confirmed. This status is most commonly assigned to SSD, NVMe, and Flash storage devices.

**Technical Background — SSD/NAND Limitation:**

Solid-state storage devices (SSD, NVMe, eMMC, Flash) use a Flash Translation Layer (FTL) that maps logical block addresses to physical NAND cells. Software-level overwrite commands write to logical addresses. The FTL may:

- Write data to new physical cells rather than overwriting existing cells (wear leveling)
- Retain data in cells marked as invalid but not yet physically erased (garbage collection latency)
- Preserve data in over-provisioning regions not accessible to the OS

As a result, a logical overwrite command does **not guarantee** that all physical NAND cells containing the previous data have been erased. This is an inherent limitation of the storage architecture, not a deficiency of SecureWipe.

**Recommended actions for** `SANITIZATION_NOT_VERIFIABLE`:
- Use AES Crypto-Erase if the drive supports hardware encryption (renders all data cryptographically inaccessible)
- Use manufacturer-provided Secure Erase command if available and verified
- Apply physical destruction (degaussing is ineffective on SSD/Flash; shredding is effective)
- Consult applicable policy (e.g., NIST SP 800-88 Rev.1 Section 2.4 for SSD guidance)

**Implication for lifecycle:** The lifecycle decision engine will default to recommending disposal (not reuse) for this status under GOVERNMENT policy. DEFAULT and ENTERPRISE policies may permit reuse with acknowledged risk documentation.

---

### `SANITIZATION_FAILED`

**Meaning:** The sanitization operation did not complete successfully, or verification detected residual data following the operation. The device must not be reused or resold.

**Criteria (any one sufficient):**
- Operation completion status: `FAILED` or `ABORTED` with significant incomplete coverage
- `verification.residual_data_detected` = `true`
- Error count exceeds policy-acceptable threshold
- Recovery assessment found recoverable fragments above policy threshold

**Implication for lifecycle:** Secure disposal is mandatory. The device must not enter any reuse or resale stream.

---

### `DISPOSAL_REQUIRED`

**Meaning:** The device has been assessed as requiring secure disposal regardless of sanitization outcome. This status may be assigned by the lifecycle decision engine (not the certificate engine alone) based on policy, device condition, or organizational mandate.

**Trigger examples:**
- Device hardware failure precluding reliable sanitization
- Policy mandate (e.g., GOVERNMENT profile mandating physical destruction for classified media)
- Operator-initiated disposal flag
- SSD/NVMe device under a policy that mandates physical destruction for all solid-state media

**Implication for lifecycle:** Initiate disposal workflow. Recycler handover record required.

## Integrity Mechanism

### SHA-256 Digest Computation

The certificate integrity digest is computed as follows:

1. Serialize all certificate fields **except** the `integrity` block itself to a canonical JSON string
2. Field ordering is deterministic: fields are sorted alphabetically at each nesting level
3. JSON serialization uses no extra whitespace (compact form), UTF-8 encoding
4. Compute SHA-256 over the UTF-8 byte string of the canonical JSON
5. Store the resulting 64-character hex digest in `integrity.digest`
6. Store the ordered list of field paths included in `integrity.digest_input_fields`

**Verification** re-performs steps 1-4 on the stored certificate (excluding the `integrity` block) and compares the computed digest to `integrity.digest`. A mismatch indicates the certificate was modified after generation.

> **IMPORTANT: SHA-256 provides integrity (tamper detection) but NOT authenticity (proof of origin).**
>
> The SHA-256 digest confirms that the certificate has not been altered since it was generated. It does **not** prove:
> - Who generated the certificate
> - That the certificate was generated by an authorized installation of SecureWipe
> - That the certificate was not generated by a malicious actor who also computed a valid digest
>
> Cryptographic authenticity requires a **digital signature** using an asymmetric key pair managed by a PKI or HSM. This infrastructure is architecture-ready in Phase 5 but not yet deployed.

### Future: Digital Signature Architecture (ARCHITECTURE READY)

The certificate schema includes `integrity.signature`, `integrity.signature_algorithm`, and `integrity.signing_key_id` fields reserved for digital signatures. The planned architecture:

- **Algorithm:** Ed25519 (preferred) or RSA-4096 with SHA-256
- **Key management:** HSM (Hardware Security Module) or software-based PKI
- **Signing input:** The same canonical JSON used for SHA-256 digest
- **Verification:** Standard asymmetric signature verification using the public key identified by `signing_key_id`

These fields are present in the schema but carry `null` values until the signing infrastructure is deployed.

## Verification Procedure

To verify a SecureWipe certificate:

**Step 1: Retrieve the certificate**
- Obtain the certificate JSON from the SecureWipe compliance database or export file
- Confirm `schema_version` is `"1.0"`

**Step 2: Extract the digest**
- Read `integrity.digest` — this is the stored SHA-256 hex string
- Read `integrity.algorithm` — must be `"SHA-256"`

**Step 3: Reconstruct the digest input**
- Remove the `integrity` block from the certificate object
- Serialize the remaining fields to canonical JSON (fields sorted alphabetically, compact, UTF-8)
- Confirm field inclusion matches `integrity.digest_input_fields`

**Step 4: Compute digest**
- Compute SHA-256 over the UTF-8 bytes of the canonical JSON string from Step 3

**Step 5: Compare**
- Compare the computed digest to the stored `integrity.digest`
- If equal: certificate has not been tampered with since generation
- If not equal: certificate has been modified; treat as invalid

**Step 6: Contextual review**
- Review `assurance_status` and its implications
- Review `device.storage_class` — if SSD/NVMe/FLASH, note limitations described under `SANITIZATION_NOT_VERIFIABLE`
- Review `verification.verification_confidence` — values below 0.8 indicate lower confidence
- Review `recovery_assessment.recovery_score` if performed

> **Note:** Digest verification confirms integrity only. It does not confirm that the underlying operation was performed correctly, that the device metadata is accurate, or that the operator identity is valid. These require organizational controls.
